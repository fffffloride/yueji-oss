# 后台排序体验重设计

## 背景与现状

代码盘点发现 12 个管理端页面暴露了排序字段：

- 业务页面：商品分类、商品、会员等级、Banner、公告、代理类型、分销等级。
- 系统页面：部门、角色、菜单、字典项、租户套餐。

其中租户套餐只有管理端模板，本仓库服务端没有对应业务或接口；悦己也没有租户概念，因此不纳入排序改造并隐藏对应菜单。最终改造范围是 11 个真实页面。

当前页面普遍在新增或编辑弹窗中暴露 `sort` 数字输入框，列表只展示原始数字。服务端按 `sort ASC` 查询，但页面没有解释方向、重复值的处理或最终位置。用户必须打开弹窗、猜测数字、保存、返回列表验证。分页和树形页面尤其难用，且现有接口只能逐条修改完整对象，没有专用移动能力。

两个页面还存在业务语义问题：

- 会员等级实际先按累计实付门槛排序，门槛又是唯一值，`sort` 几乎不会影响结果。
- 分销等级的 `rank` 参与自动升级，另有 `sort` 控制列表展示；同一等级有两套顺序，容易配置矛盾。

## 目标

- 用户直接操作“当前位置”，不再理解或维护数据库排序值。
- 短列表支持拖拽，长列表支持精确移动，树形列表只在同级内排序。
- 每次操作即时保存，并明确显示保存中、已保存或失败回滚。
- 保留升级前的展示顺序，不因重复或缺省 `sort` 值发生跳变。
- 不改变会员等级判定、分销自动升级、菜单权限和部门归属等业务规则。

## 设计决策

采用混合排序，不建设独立排序工作台：

- 短平铺列表：Banner、公告、代理类型、角色、字典项使用拖拽；同时提供上移、下移和移至第 N 位。
- 树形列表：商品分类、部门、菜单只允许同一父节点下拖拽；跨父级移动仍通过编辑表单修改归属。
- 长列表：商品显示“全局第 X / N 位”，提供置顶、上移、下移和移至第 N 位。筛选只用于定位商品，排序始终作用于全局列表。
- 会员等级：移除手工排序，固定按累计实付门槛升序展示和判定。
- 分销等级：移除独立 `sort`，只保留业务字段 `rank`；列表按 `rank` 升序。编辑 `rank` 时明确提示它会影响自动升级规则，并继续校验唯一性。

所有列表不再显示或编辑原始 `sort`，改为显示一位起始的“位置”。停用或隐藏项目仍参与位置计算，重新启用后回到原位置。

## 交互流程

### 拖拽

用户按住行首手柄移动项目。页面立即显示新位置，工具栏显示“保存中”。该项目在请求完成前不可再次移动；其他操作进入同一页面的串行队列。

保存成功后显示短暂的“已保存”，并用服务端返回的权威顺序刷新列表。保存失败时停止后续队列，回滚到最后一次成功快照，提示“排序保存失败，已恢复”，并提供重试。

拖拽只在未筛选列表中启用，并作用于当前可见行对应的全局位置；跨分页移动使用“移至第 N 位”。存在关键词或状态筛选时，页面禁用拖拽并提示先清除筛选，但仍允许按全局位置精确移动。

### 精确移动

“置顶”“上移”“下移”直接执行一次移动。“移至”打开轻量输入框，显示允许范围 `1–N`；非法位置不发送请求。商品在筛选状态下仍显示全局位置和全局总数。

拖拽不是唯一入口。所有页面保留可聚焦的上移、下移和移至操作，确保键盘用户能完成相同任务。

## 服务端契约

每个资源增加单项移动接口，复用原有更新权限，不新增排序权限：

```text
PATCH /<resource>/:id/position
{ "position": 6, "parentId": "..." }
```

`position` 是用户可见的一位起始位置。树形资源必须提交当前 `parentId`，服务端只在该父节点的兄弟项目中移动；目标项目不存在、父节点不一致或位置越界时返回业务错误。

服务端在单个数据库事务中读取当前权威顺序、移动目标项目并重排受影响区间。接口返回目标项目最终位置；客户端成功后重新请求当前页或当前树，以服务端查询结果为准。客户端不提交整张列表，因此并发操作不会用旧快照覆盖无关项目。

新增和编辑 DTO 将 `sort` 改为可选。旧客户端传入时仍接受该字段，新版管理端不再发送；服务端在缺省时把新项目追加到当前作用域末尾。会员等级忽略 `sort`，分销等级仅使用 `rank`。

## 数据迁移

上线前按各资源当前实际查询规则读取数据，并在原作用域内生成连续位置：

- 平铺列表按现有 `sort` 及当前次级排序字段确定稳定顺序。
- 商品分类、部门、菜单分别在每个父节点下编号。
- 停用和隐藏数据一起编号并保留当前相对位置。
- 会员等级以累计实付门槛为准；分销等级以 `rank` 为准，不迁移冗余展示顺序。

迁移前后，小程序和管理端的初始展示顺序必须一致。本版本保留底层 `sort` 列以兼容旧代码；确认生产稳定后，再用独立清理任务删除会员等级与分销等级的冗余列。

## 上线顺序

1. 执行旧数据归一化，并上线单项移动接口。
2. 验证旧管理端和小程序展示顺序未变化。
3. 上线新版管理端，移除 `sort` 输入与原始数字列，启用位置操作和保存状态。
4. 隐藏租户套餐入口；不补建租户模块。

## 错误与边界

- 保存失败：自动回滚并允许重试，不保留半成功状态。
- 快速连续操作：按页面串行提交；前一请求失败后停止队列并刷新权威数据。
- 分页或筛选：位置始终是全局位置；筛选状态禁用拖拽，跨页操作使用“移至第 N 位”。
- 权限不足：不显示拖拽手柄和移动操作；服务端仍校验原更新权限。
- 树形跨级拖拽：客户端禁止，服务端再次校验父节点。
- 项目在并发操作中被删除或停用：服务端返回当前权威结果，客户端刷新并说明原因。
- 新增项目：追加到作用域末尾，避免默认 `sort=0` 抢占首位。

## 验收与测试

- 移动一次后刷新页面，顺序保持；同一作用域的位置连续且不重复。
- 保存失败时页面恢复旧顺序，并出现失败原因和重试入口。
- 商品在任意筛选条件下都显示和修改全局位置。
- 商品分类、部门、菜单不能通过排序操作跨父级。
- 无更新权限账号无法发起移动；直接调用接口也被拒绝。
- 会员等级判定仍只由累计实付门槛决定。
- 分销自动升级仍只由 `rank` 和升级门槛决定。
- 停用项目重新启用后恢复原相对位置。
- 鼠标拖拽与键盘位置操作得到相同结果。
- 数据迁移前后，小程序首页 Banner、公告、默认商品顺序保持不变。

服务端为移动区间、首尾位置、同级限制和事务回滚各保留最小可运行测试；管理端至少覆盖成功保存、失败回滚和筛选下全局位置三个交互检查。

## 未采用方案

- 继续在表格或弹窗内编辑数字：改动小，但仍要求用户心算顺序，无法解决重复值和分页定位。
- 独立排序工作台：可提供预览、历史和定时发布，但 11 个页面多数为低频配置，建设和维护成本高于当前需求。
- 当前筛选结果内排序：会让同一商品在不同筛选条件下产生不一致含义，与现有全局 `sort` 数据模型冲突。
